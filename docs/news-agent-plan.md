# SURE-EVAL News Agent 方案

状态：首版已实现，真实模型与旧 PR 回放验证完成；独立 `news-agent` 环境和
dry-run 定时器已部署。实现保留本地，未提交主分支，未创建新 PR。

基线：`main` 分支，HEAD `3853dab`（2026-11-18，合并 PR #49）

## 目标

在 SURE-EVAL README 中提供一个清晰的“最近支持”公告栏，告诉用户：

- 最近新增了什么评测能力；
- 对应的 task、metric 和精确 `pipeline_id`；
- 从输入到 `report.json` 的实际评测链路；
- 任务文档、pipeline catalog 和源代码变更的位置。

公告由独立的 `news-agent` 自动发现和生成。它固定调用 Kimi Code
`k3.1-pro`，定期检查 `sure-evaluation` 主分支的新提交和文件修改，发现
新的 task、metric、node、route 或 pipeline 后生成公告更新。

## 已确认的 EAR-1 事实

当前仓库支持的是 **EAR-1**，不是名为 `ear-v1` 的软件版本。EAR-1 是
ICASSP 2027 Grand Challenge 的评测项目；`v1` 出现在 conversion、normalization
和 scorer 的节点版本中。

当前主分支有两条 EAR-1 路线：

| 任务 | 指标 | 精确 pipeline ID | 链路 |
| --- | --- | --- | --- |
| SD | DER | `sd.any.der.conversion_sd_ear1_submission_v1.ear1_scorer_v1` | `conversion/sd__ear1_submission` → `scoring/ear1_scorer` |
| SA-ASR（zh） | cpCER | `sa_asr.zh.cpcer.conversion_sa_asr_ear1_submission_v1.ear1_norm_v1.ear1_scorer_v1` | `conversion/sa_asr__ear1_submission` → `normalization/ear1_norm` → `scoring/ear1_scorer` |

因此第一条公告应命名为 **“EAR-1 评测支持”**，可以在正文中说明使用了
v1 节点版本，不能把它写成“EAR-v1”。公告内容必须引用：

- `docs/tasks/sd.md`；
- `docs/tasks/sa_asr.md`；
- `docs/pipeline_catalog.jsonl`；
- 对应的 EAR-1 合并提交和测试结果。

## 与 `sure-maintainer` 的隔离要求

`news-agent` 是全新的独立 agent。可以参考 `sure-maintainer` 的幂等、重试、
证据冻结和 Kimi JSON 输出思路，但实际实现不能共享：

- 不导入 `sure-maintainer` 的 Python 模块；
- 不读取或写入 `sure-maintainer` 的 SQLite 数据库；
- 不使用其配置文件、prompt、state、outbox 或日志目录；
- 不复用其 systemd service、timer 或进程锁；
- 不加入其 PR 审阅、飞书通知和 Wiki 同步流程；
- 不使用其模型或其他运行配置；运行时仅读取 news-agent 自己的密钥变量。

新 agent 使用自己的配置、状态库、密钥变量、prompt、schema、锁和部署单元。
Kimi 模型仍为 `k3.1-pro`。按用户本轮授权，两个服务使用同一个 key；部署时
将其复制到独立凭据文件的 `NEWS_AGENT_KIMI_API_KEY`，运行时不加载
sure-maintainer 的 `.env`，其余配置、日志和状态保持独立。

## 自动检测链路

每个轮询周期执行以下步骤：

```text
GitHub API / 独立 checkout
        ↓
读取主分支最新 commit SHA
        ↓
与 news-agent 自己的 cursor 比较
        ↓
读取新增 commit 的变更文件和 diff
        ↓
筛选 task、route、node、conversion、catalog、任务文档变化
        ↓
从当前主分支的 manifest、routes.yaml、pipeline_catalog.jsonl 提取事实
        ↓
检测是否出现新的可用 pipeline 或支持能力
        ↓
调用 Kimi Code k3.1-pro 生成英文摘要
        ↓
校验 schema、来源、pipeline ID、节点和链接
        ↓
生成公告数据、完整公告页和 README 公告区
        ↓
运行 Markdown、链接、catalog 和测试检查
        ↓
dry-run、创建文档 PR，或按配置提交文档更新
```

没有新增支持证据的提交不得生成公告。例如只修改格式、测试、依赖锁文件
或内部重构时，agent 只推进 cursor，不调用 Kimi。

同一变更使用以下幂等键，避免重复公告和重复模型调用：

```text
repository + base_branch + head_sha + catalog_digest + prompt_version + model
```

模型失败、schema 校验失败、链接失效或发布失败时保留队列记录和错误原因，
不覆盖当前 README，不推进对应的成功 cursor。

## Kimi 输入和输出边界

Kimi 输入是程序冻结的结构化证据，包括：

- commit SHA、PR 或提交链接；
- 变更文件列表和受限 diff；
- 新增或变化的 pipeline catalog 行；
- task manifest、route 和 node manifest；
- 已存在的英文公告格式和语气规则。

Kimi 只能输出：

- 英文标题和摘要；
- 面向用户的能力说明；
- 对确定性链路的自然语言解释；
- 使用限制和迁移提示。

以下字段必须由程序生成或校验，模型不能决定：

- `id`、发布日期和版本号；
- `task`、`metric`、`pipeline_id`；
- 节点顺序和节点版本；
- 源代码、文档和 commit 链接；
- README 可写范围；
- 是否真的属于“新增支持”。

## 公告数据契约

第一版建议使用 YAML，方便维护者手工修订模型生成的文案：

```yaml
id: ear-1
status: supported
published_at: 2026-11-18
title: EAR-1 evaluation routes are supported
summary: ""
support:
  tasks: [sd, sa_asr]
  metrics: [der, cpcer]
  pipeline_ids: []
chain:
  - task: sd
    pipeline_id: "..."
    nodes: []
  - task: sa_asr
    pipeline_id: "..."
    nodes: []
links:
  docs: []
  catalog: docs/pipeline_catalog.jsonl
  source_change: ""
evidence:
  source_commit: ""
  source_files: []
  model: k3.1-pro
  prompt_version: news_v1
```

`news-entry.v1.json` 负责结构校验；`renderer.py` 负责排序、截取最近公告、
生成英文页面和 README 标记区。已发布 entry 默认不可原地改变事实，修订
使用 `revision` 和 `supersedes` 留下历史。

## README 展示

英文 README 保留以下标记：

```md
<!-- SURE-NEWS:START -->
<!-- generated by news-agent; do not edit inside this block -->
<!-- SURE-NEWS:END -->
```

生成区展示最近三条公告，每条包含：状态徽章、支持内容、精确 pipeline、简化
链路和“完整公告 / 任务文档 / 源变更”链接。完整历史写入
`docs/news/index.md`，不把所有历史内容堆在 README 首页。

EAR-1 示例应呈现为：

```text
🆕 EAR-1 · 已支持

SD / DER：submission conversion → EAR-1 scorer → report.json
SA-ASR / zh / cpCER：submission conversion → EAR-1 normalization
                 → EAR-1 scorer → report.json
```

这段展示必须使用 catalog 中的精确 pipeline ID，并链接到
`docs/tasks/sd.md`、`docs/tasks/sa_asr.md` 和对应源提交。

## 发布策略

发布模式分三级：

1. `dry-run`：只生成预览和 diff，不写远端；第一阶段默认使用。
2. `pr`：自动创建只修改公告文件的 GitHub PR；推荐生产默认模式。
3. `docs-commit`：只允许写入 `docs/news/**`、`README.md`
   和可选的 `NEWS.md`，不自动合并代码变更。

`news-agent` 永远不修改评测代码、route、node manifest、pipeline catalog
或 CI 配置。catalog 由已有的确定性生成命令更新；新闻 agent 只能读取它。

## 测试和验收

第一版至少包含：

- EAR-1 两条 pipeline 的事实提取测试；
- 不存在的 pipeline ID 会阻止发布；
- 节点顺序与 route/catalog 不一致会阻止发布；
- README 只允许修改 `SURE-NEWS` 标记区；
- 英文 entry 的 ID 唯一且历史完整；
- 同一 commit/cursor 不会重复调用 Kimi；
- Kimi 超时、截断、无效 JSON 时不产生半成品；
- 链接、软链接和 Markdown 渲染检查；
- dry-run 不写远端、不读取 `sure-maintainer` 状态；
- 独立 service、锁、日志和 state 路径检查。

验收顺序：先用 EAR-1 做本地 fixture，再用真实 `k3.1-pro` 做一次只读
smoke，随后运行 `dry-run`，最后才启用自动创建 PR。自动合并不属于第一版。
